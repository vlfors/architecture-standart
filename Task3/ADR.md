#### Обоснование решения

1. Интеграционный слой (API Gateway, кэш, брокер сообщений)

    Внедрение интеграционного слоя между фронтенд-системами и АБС необходимо для снижения нагрузки на АБС (NF4)
    API Gateway  обеспечивает единую точку доступа к бэкенд-системам, унифицирует API и упрощает интеграцию
    Redis используется для кэширования часто запрашиваемых данных (справочники, актуальные ставки), что снижает время отклика (NF3)
    RabbitMQ выбран вместо Kafka (несовместимость с текущей архитектурой интернет-банка), обеспечивает асинхронную обработку заявок

2. Модификация существующих систем

    Сайт ( Java Spring Boot  + React.js): добавление формы заявки на депозит и интеграция с API Gateway
    Интернет-банк (ASP.NET MVC 4.5): добавление функционала оформления депозитов и интеграция с API Gateway
    АБС (Oracle + PL/SQL): добавление интерфейса управления ставками и интеграция с интеграционным слоем
    Система кол-центра (React.js + Java Spring Boot): минимальные доработки для получения заявок с сайта
3. Выбор технологий
    Kong gateway  для API Gateway: Kong Gateway обеспечивает безопасность, масштабируемость и отказоустойчивость для API, поддерживая аутентификацию, шифрование, мониторинг и интеграцию с банковскими системами.
    Redis: высокопроизводительное решение для кэширования, снижает время отклика до миллисекунд (NF3)
    RabbitMQ: стабильный и проверенный брокер сообщений, обеспечивает надежную передачу заявок и других событий

4. Обеспечение надежности и производительности

    Горизонтальное масштабирование для интеграционного слоя, сайта и интернет-банка (NF6)
    Репликация Redis и RabbitMQ между основным и резервным ЦОД (NF2)
    Балансировка нагрузки через API Gateway (NF6)
    Кэширование для снижения времени отклика (NF3)

5. Обеспечение безопасности

    Шифрование данных при передаче (HTTPS, TLS не ниже 1.2) (NF5)
    Аутентификация и авторизация API через API Gateway
    Централизованное логирование и мониторинг (NF9)



### <a name="_bjrr7veeh80c"></a>**Альтернативы**
Опишите здесь наиболее важные альтернативные решения.

Альтернатива 1: Прямая интеграция интернет-банка с АБС

Преимущества: более простая архитектура, меньше компонентов для разработки
Недостатки: высокий риск перегрузки АБС (NF4), отсутствие масштабируемости, более сложная реализация отказоустойчивости

Альтернатива 2: Использование Kafka вместо RabbitMQ

Преимущества: лучшая масштабируемость, подготовка к будущему переходу на микросервисы
Недостатки: несовместимость с текущей архитектурой интернет-банка, необходимость более глубокой модернизации и обучения персонала

Альтернатива 3: Разработка микросервисного депозитного модуля

Преимущества: современная архитектура, лучшая масштабируемость и гибкость
Недостатки: существенно больший объем работ, выходящий за рамки MVP, сложности с интеграцией в существующий ландшафт

**Недостатки, ограничения, риски**

Подробно опишите здесь недостатки, ограничения и риски выбранного решения.

1. Проблемы интеграции: Возможны сложности при интеграции различных систем и технологий (особенно при взаимодействии с АБС)
2. Перегрузка АБС: Несмотря на внедрение интеграционного слоя, существует риск превышения возможностей АБС при росте нагрузки
3. Масштабирование решения: В будущем потребуется более фундаментальная модернизация для обеспечения растущих потребностей бизнеса
4. Зависимость от подрядчиков: Модификации ядра интернет-банка и системы кол-центра зависят от подрядчиков, что может увеличить сроки и стоимость
5. Временное решение: MVP может закрепиться как постоянное решение, что затруднит дальнейшую модернизацию систем
